# Verification

- Check the selected operations against the source OpenAPI contract before writing tests: method/path, parameter location and types, body shape, declared statuses, response media types, and headers. Exercise behavior that is actually implemented, including relevant failure cases.
- Use the project's existing JUnit 5, Spring test, and mocking conventions. Test application decisions independently of HTTP; test controller/adapter mapping and statuses at the boundary. Do not add tests that merely repeat getters or mock away the behavior under test.
- Run `./mvnw clean verify` (Windows: `.\mvnw.cmd clean verify`) with the project's JDK, profiles, and Maven settings. If the project has a Spring Modulith boundary test, run it as part of verification. If OpenAPI Generator is configured, confirm generation succeeds and the controller implements its generated interface without duplicate DTOs or routes.
- Start the application and exercise the selected endpoints and health check when the environment supports it. Use contract-consistent requests; avoid real external providers or destructive data operations unless the task requires them. An environment failure must be distinguished from a code failure with the command, error, and log path.
- A module is not complete while required behavior is a placeholder, a mandatory check fails, or a contract mismatch remains. Report the precise unresolved dependency on developer input or environment if completion is blocked.
- Logging: confirm each state-changing use case emits exactly one clear business-event line, no sensitive data is logged, and no exception is logged twice. With the app running in a non-`local` profile, call one endpoint and check that the JSON line carries `requestId` and the expected key-values.
